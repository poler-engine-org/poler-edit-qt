# Архитектура `POLER OS-Translator`: Двухъядерный мост уровня POST (BIOS/UEFI) между Windows и Linux

> **Автор концепции и архитектуры**: Виталий Коток (`Kotokvit`)  
> **Связанные документы**: [`docs/MANIFESTO_TRIT_ZERO_SINUS.md`](./MANIFESTO_TRIT_ZERO_SINUS.md), [`src/boxenv/mod.rs`](../src/boxenv/mod.rs), [`src/gateway/mod.rs`](../src/gateway/mod.rs)

---

## 1. Суть проблемы: почему Windows и Linux не могут общаться нативно при обычной загрузке

В классической схеме на компьютере загружается только **одно** ядро (либо Windows NT, либо Linux), которое монопольно забирает себе процессор, оперативную память и таблицы BIOS/UEFI:

1. **Проблема жёсткого ядра Linux (`seccomp` / `userns` / паника ядра)**:
   * На Linux изоляция (`poler-box`, `unshare`, `pivot_root`, `seccomp`) работает на уровне жёстких запретов системных вызовов. Любой процесс, которому нужен прямой разговор с ядром за пределами узкого белого списка сисколлов, мгновенно убивается (`SIGSYS` / `EPERM`), а при сбое драйвера или перегрузке подсистемы памяти ядро Linux уходит в `kernel panic` / `hard lockup` и физически вырубает или вешает ПК.
   * На Windows ядро NT гораздо мягче относится к пользовательским процессам (`ntdll.dll` / `Win32`), поэтому тяжёлые приложения, графика и процессы, активно говорящие с ядром, не вылетают и не роняют хост-машину.

2. **Проблема инициализации Windows из-под POST (BIOS / UEFI)**:
   * Ядру **Linux (`vmlinuz`)** после старта не нужен BIOS/UEFI: его можно положить в любую область RAM, заполнить страницу `boot_params` (4 КБ) и передать управление на `startup_64`.
   * Загрузчик и ядро **Windows (`bootmgfw.efi` → `winload.efi` → `ntoskrnl.exe`)** жёстко требуют живых таблиц **UEFI Boot Services** (`GetMemoryMap`, `ExitBootServices`, `ACPI RSDP`, `GOP Framebuffer`), которые существуют **только сразу после прохождения POST материнской платы**.
   * Как только первая загрузившаяся ОС вызывает `ExitBootServices()`, таблицы POST уничтожаются. Поэтому «дозапустить» нативное ядро Windows из-под уже работающего Linux (чтобы в два клика открыть `.exe` без кривых эмуляторов типа Wine и без тяжёлых виртуальных машин) невозможно, если Windows не была проинициализирована ещё на этапе POST.

---

## 2. Решение: `POLER OS-Translator` — запуск ДО обеих ОС прямо из-под POST

Между железом (BIOS/UEFI POST) и операционными системами (Windows и Linux) ставится **четырёхмодульный `POLER OS-Translator`**, который стартует **первым** сразу после POST и управляется:
* **отдельно (до загрузки ОС)** — в автономном режиме отладки, шелла и расчётов прямо на голом железе;
* **из-под Windows** — через `poler-engine.exe` (`--gateway` / `--shell` / GUI);
* **из-под Linux** — через бинарник `poler-engine` (`--gateway` / `--shell` / `poler-box`).

```
┌──────────────────────────────────────────────────────────────────────────┐
│ 0. BIOS / UEFI POST (инициализация CPU, RAM, ACPI, PCIe, GOP-видеокарты) │
└────────────────────────────────────┬─────────────────────────────────────┘
                                     ▼
╔══════════════════════════════════════════════════════════════════════════╗
║ МОДУЛЬ 1: POLER PRE-BOOT TRANSLATOR (crates/poler-boot, BOOTX64.EFI)     ║
║ • Запускается ПЕРВЫМ сразу после POST (до Windows и до Linux)            ║
║ • Выделяет в физической памяти невыгружаемое окно POLER Shared RAM Ring  ║
║   (инициализируется тритным вакуумом 121 = 0x79)                         ║
║ • Даёт 4 режима работы:                                                  ║
║   [1] Автономная отладка / Калькулятор / Шелл прямо поверх POST          ║
║   [2] Чистый запуск только Windows                                       ║
║   [3] Чистый запуск только Linux                                         ║
║   [4] Двухъядерный режим (Dual-POST: инициализация обоих ядер из POST)   ║
╚═════════════════╦════════════════════════════════════╦═══════════════════╝
                  ║                                    ║
     МОДУЛЬ 2: Тонкий арбитр Ring -1 (VMX / SVM) и Dual-POST парковка
                  ║                                    ║
                  ▼                                    ▼
┌─────────────────────────────────┐  ┌─────────────────────────────────────┐
│        ЯДРО WINDOWS (NT)        │  │             ЯДРО LINUX              │
│ • Прошло родную инициализацию   │  │ • Живёт в выделенной зоне памяти /  │
│   winload.efi прямо из POST!    │  │   ядрах CPU                         │

│   процессы без seccomp-вылетов  │  │   (unshare / pivot_root / seccomp)  │
└─────────────────▲───────────────┘  └─────────────────▲───────────────────┘
                  │                                    │
                  └───────────► ╔════════╗ ◄───────────┘
                                ║ МОДУЛЬ ║
                                ║   3    ║  POLER Shared RAM Ring

                                ╚════════╝   обмен за наносекунды без сети)
```

## 3. Четыре модуля системы

### Модуль 1. `poler-boot.efi` (`crates/poler-boot`) — Загрузчик-Транслятор и POST-Отладчик
* **Формат**: нативный `no_std` бинарник `PE32+` (`x86_64-unknown-uefi`) без единой внешней зависимости.
* **Точка старта**: `\EFI\BOOT\BOOTX64.EFI` (или `\EFI\POLER\poler-boot.efi`), вызывается прошивкой материнской платы сразу после завершения POST.
* **Задачи на этапе POST**:
  1. До того как любая ОС затрёт UEFI Boot Services, выделяет через `AllocatePages(AllocateAnyPages, EfiReservedMemoryType)` физическое окно **`POLER Shared RAM Ring`** (выровненное по границе 4 КБ/2 МБ), которое ни Windows, ни Linux не имеют права перезаписывать или выгружать в своп.
  2. Заполняет буфер данных тритным вакуумным нулём (`0x79 = 121 = (3^5 - 1)/2`) и прописывает в заголовок физические адреса очередей `Win -> Lin` и `Lin -> Win`, таблицу ACPI `RSDP` и параметры видеорежима `GOP`.
  3. Запускает интерактивную консоль **POST-Отладчика (`poler-post>`)**:
     * проверка аппаратных возможностей процессора через `CPUID` (`VMX` / Intel VT-x, `SVM` / AMD-V, `AVX2`);
     * встроенный целочисленный/проективный калькулятор `[N:D]` с Абсолютным Нулём (`D = 0` — полюс без исключения процессора `#DE`);
     * прямой просмотр физической памяти и таблиц UEFI;
     * запуск Windows в одиночку, Linux в одиночку, либо в двухъядерном режиме.

### Модуль 2. `poler-hv` — Тонкий арбитр процессора (`Ring -1`, `VMX` / `SVM`) и Dual-POST инициализация
* Чтобы Windows могла запустить `.exe` в два клика из-под Linux (и наоборот), **оба ядра получают инициализацию из POST**:
  1. На этапе POST арбитр поднимает минимальный контур аппаратной виртуализации (`VMXON` на Intel / `SVME` на AMD — без гигабайтного QEMU/Hyper-V, только таблицы `EPT`/`NPT` для разделения физической памяти и ядер CPU).
  2. **Ядро Windows (`winload.efi` → `ntoskrnl.exe`)** проходит полную штатную инициализацию, пока живы таблицы UEFI POST. Если пользователь выбрал основной рабочей средой Linux, проинициализированное ядро Windows переводится в состояние мгновенной «тёплой парковки» в RAM (или остаётся дежурить на 1 выделенном потоке CPU).
  3. **Ядро Linux (`vmlinuz`)** стартует параллельно по прямому 64-битному протоколу загрузки (`boot_params`), получая указатель на то же самое физическое окно `POLER Shared RAM Ring`.
  4. **Изоляция сбоев**: если внутри ядра Linux срабатывает `seccomp KILL`, `OOM-killer` или даже `kernel panic`, арбитр `Ring -1` перехватывает остановку только Linux-контура — хост-машина и ядро Windows продолжают работать без малейшего сбоя, а Linux-ядро может быть перезапущено в своей области RAM за доли секунды.

### Модуль 3. `poler-bridge` — Нативная шина между двумя ядрами в физической памяти (`POLER Shared RAM Ring`)
* Вместо медленных сетевых мостов (`TCP/IP`, `virtio-net`, `9p`, `SMB`), которые теряют миллисекунды на системных вызовах и копировании буферов, оба ядра отображают (`MmMapIoSpace` в Windows / `ioremap_cache` или `/dev/mem` в Linux) **один и тот же физический регион оперативной памяти**, созданный Модулем 1 при POST:
  ```text
  Физическое окно POLER Shared RAM Ring (выделено при POST в EfiReservedMemoryType):
  ┌──────────────────────────────────────────────────────────────────────┐
  │ 0x0000..0x0FFF (4 КБ)  : Заголовок PolerRingHeader                   │
  │   • magic              : "POLER_OS" (0x534F_5245_4C4F_505F)          │
  │   • version            : 1                                           │
  │   • vacuum_byte        : 0x79 (121 — тритный вакуум 00000_3)         │
  │   • win_state / lin_state : статус готовности обоих ядер             │
  │   • win_to_lin_head/tail  : атомарные указатели очереди Win -> Lin   │
  │   • lin_to_win_head/tail  : атомарные указатели очереди Lin -> Win   │
  ├──────────────────────────────────────────────────────────────────────┤
  │ 0x1000..0x200FFF (2 МБ): Кольцевая очередь команд и RPC Win -> Lin   │
  ├──────────────────────────────────────────────────────────────────────┤
  │ 0x201000..0x400FFF(2 МБ): Кольцевая очередь команд и RPC Lin -> Win  │
  ├──────────────────────────────────────────────────────────────────────┤
  │ 0x401000..Конец окна   : Zero-Copy область данных (.poler, .t5c,     │
  │                          общий кадровый буфер окон и аудиопоток)     │
  └──────────────────────────────────────────────────────────────────────┘
  ```

### Модуль 4. Двусторонний запуск в два клика (`poler-engine` на Windows и Linux)
* **Сценарий А (Вы работаете в Windows → двойной клик по Linux-программе или `.poler`-коробке)**:
  1. `poler-engine.exe` кладёт задачу в очередь `Win -> Lin` внутри `POLER Shared RAM Ring`.
  2. Уже прогретое ядро Linux мгновенно забирает задачу, запускает ELF-бинарник внутри `poler-box` (`unshare` + `pivot_root` + `seccomp`), и пишет результат/окно обратно в общее кольцо RAM.
  3. Даже если процесс в Linux требует специфичных ядерных вызовов или падает — Windows остаётся абсолютно неуязвимой.
* **Сценарий Б (Вы работаете в Linux → двойной клик по Windows-программе или игре `.exe`)**:
  1. `poler-engine` на Linux не запускает эмулятор Wine, а кладёт команду запуска `.exe` в очередь `Lin -> Win`.
  2. Настоящее ядро Windows (прошедшее честную инициализацию из-под POST!) запускает `.exe` нативно, со 100%-й совместимостью с драйверами и `ntdll.dll`, а картинка окна передаётся через общую область `Zero-Copy Framebuffer` в `POLER Shared RAM Ring`.
* **Сценарий В (Режим отладки Транслятора между двумя ОС)**:
  1. Из Windows (`poler-engine.exe --gateway`), из Linux (`poler-engine --gateway`) или прямо на этапе POST (`poler-post>`) разработчик видит состояние кольца `POLER Shared RAM Ring`, счётчики пакетов между ядрами, переводы путей (`C:\...` ↔ `/rootfs/...`) и вердикты безопасности.
